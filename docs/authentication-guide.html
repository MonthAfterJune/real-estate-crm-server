How login and sign-up work
in React and .NET

Start with the browser. Follow one request into the backend. Then see how the server remembers who you are.

This guide explains the implementation in your projects: realestateCRM-client (React) and CRM (ASP.NET Core and PostgreSQL). It assumes you are new to backend development. The diagrams are built into this file and work offline.

React asks. The server decides. The database stores the records.

The key idea: React never decides whether a password is correct. ASP.NET Core Identity checks it on the server. After success, .NET issues a protected cookie, and the browser sends that cookie with later API requests.

01 • Vocabulary

Imagine Meridian as an office. The form is the reception desk, the API is the staff checking details, and the database is the filing system. A session cookie is a temporary access pass protected by the server.

02 • Registration

What happens when you click “Create account”

Sign-up creates a new account. In this implementation, successful sign-up also logs you in immediately.

  1. You fill in the form. Signup.tsx collects name, email, role, password, confirmation, and the demo acknowledgment. It checks that passwords match. Confirmation stays in React and is not sent to .NET.
  2. React gets a CSRF token. The API client calls GET /api/auth/csrf before its first write. The browser receives an antiforgery cookie; JavaScript receives the matching request token.
  3. React sends the request. authService.register() sends JSON, the X-CSRF-TOKEN header, and credentials: 'include'.
  4. .NET validates independently. The CSRF filter rejects an invalid token. Request validation checks email, name, password length, acknowledgment, and role. Public registration accepts only agent, buyer, or seller.
  5. Identity creates the account. The controller loads the role, uses email as username, and calls UserManager.CreateAsync(user, password). Identity validates its password rules, normalizes lookup fields, generates a hash, and saves through EF Core.
  6. .NET signs you in. SignInManager.SignInAsync() creates the principal and session cookie. The response contains ID, name, email, and role.
  7. React updates the screen. AuthProvider stores the account in memory and routes to its dashboard. The CSRF cache is cleared because the identity changed.
// Example request. Use your own password.
{
  "fullName": "Taylor Agent",
  "email": "taylor@example.com",
  "password": "your own long passphrase",
  "role": "agent",
  "acceptTerms": true
}

The acknowledgment is validated, but is not a legal terms system or stored consent audit. The public pages follow your supplied meridian-auth.html using the current light theme.

03 • Login

What happens when you click “Log in”

Login does not create a second user. It finds an existing account and checks the submitted password against its stored hash.

  1. Login.tsx reads email, password, and Remember me. Repeat submission is disabled while pending.
  2. The client obtains or reuses a CSRF token and posts the login JSON.
  3. AuthController.Login() trims the email and calls FindByEmailAsync(). Identity uses normalized email, so ordinary email casing does not change the account.
  4. The server reads the role from the database. The login form cannot supply a role.
  5. PasswordSignInAsync(user, password, rememberMe, lockoutOnFailure: true) checks the password and lockout. Identity supports other checks, but this project has no MFA enrollment flow.
  6. Success sets the cookie and returns account JSON. React stores the account, then opens its dashboard or the allowed page you originally tried to visit.
  7. Failure returns a generic 401. Missing accounts, wrong passwords, and locked accounts receive the same error message.

Two limits working together

LimitConfigurationPurpose
Account lockout5 failed passwords → 15-minute lockoutSlows guessing of one account. A correct password during lockout is still rejected.
Request rate limit10 register/login requests per minute per remote IPLimits bursts across both endpoints; excess requests get 429. In-memory per API process.

Successful password sign-in normally resets failed-attempt tracking. During lockout, wait 15 minutes. During rate limiting, wait for the next one-minute window. Repeated clicking does not help.

04 • Passwords

Why the database stores a hash

A plaintext password is the original password you typed. A password hash is produced by an expensive one-way process. The server verifies that result; it does not decrypt a saved password.

  • Salt: random input prevents identical passwords from producing identical stored hashes and makes precomputed password tables less useful.
  • Work factor: repeated computation makes guessing costly. The framework default is used; there is no custom cryptography.
  • Versioned format: stored hash data contains the information needed for verification. Identity can recognize older formats and upgrade hashes when its policy requires it.
  • Verification: CheckPasswordAsync() and PasswordSignInAsync() use Identity's verifier. You do not compare the typed password to PasswordHash as strings.

Account responses contain only Id, FullName, Email, and Role. General user responses also use DTOs. Neither returns password hashes or authentication internals.

Rules in this application

New passwords must be 12–128 characters and use at least 3 different characters. Request validation caps the length; Identity enforces its minimum and uniqueness rules. Digits, uppercase, and symbols are not separately required. A long, personally chosen passphrase is supported.

Hashing and HTTPS have different jobs. Hashing protects stored credentials. HTTPS protects the password in transit. The password still reaches the server during login. Never put it in URLs, logs, screenshots, or local storage.

Reference: Microsoft: Identity configuration. Your rules are in AuthenticationExtensions.cs and AuthDtos.cs.

05 • Sessions

How the app remembers you

After login, .NET sends a Set-Cookie response header. The browser stores it automatically. Later fetch requests include it because your client uses credentials: 'include'. React does not read the session cookie or save an authentication token in local storage.

SettingMeaning here
HttpOnlyJavaScript cannot read the cookie using document.cookie. This reduces one way to steal a ticket; it does not make a page immune to malicious scripts.
SameSite=StrictRestricts cookies in cross-site contexts. The frontend and API are designed to be served through the same site.
Secure in productionProduction cookies use __Host- names, HTTPS only, path /, and no Domain attribute. Development supports local HTTP tooling.
8-hour ticketThe ticket expires after 8 hours. Sliding expiration is off, so normal activity does not extend it.
Remember meChecked login creates a persistent cookie until the same 8-hour expiry. Unchecked login and registration use a browser-session cookie, also limited by ticket expiry. Browser session restoration may preserve session cookies.
Protected ticketASP.NET Core Data Protection protects the ticket against reading and tampering. Editing the cookie cannot make a buyer an agent.

Refreshing the page

  1. Reloading clears React's in-memory account.
  2. AuthProvider calls GET /api/auth/me with the cookie.
  3. Authentication middleware verifies the ticket and creates HttpContext.User.
  4. The endpoint loads the user and returns account JSON.
  5. React restores its account state. A missing/expired cookie gives 401; protected pages redirect to login.

Route guards wait for the session check. API failures show a retry message on protected pages rather than being mistaken for a successful login.

Logging out

The logout button sends a CSRF-protected POST /api/auth/logout. SignInManager.SignOutAsync() clears Identity cookies. React clears its account and token cache and opens login. A failed request displays an error instead of claiming the server session was removed.

Logout clears this browser's ticket; it does not immediately revoke every copied ticket or sign out every device. Identity validates security stamps at a 5-minute interval. UserService changes the stamp when email or role changes, rejecting older tickets at their next validation. No all-device logout UI is included.

Microsoft recommends cookies for browser applications: Identity API authorization guidance. This app uses custom controller endpoints with standard Identity services rather than the framework's generated endpoints.

06 • Request security

Why writes need a CSRF token

Browsers attach cookies automatically. Another site could try to make your browser send a write using an existing session. Cross-Site Request Forgery protection helps verify that a write came through a page able to obtain the request token.

GetAndStoreTokens() issues an HttpOnly antiforgery cookie and returns a request token in JSON. React stores that token in memory and sends X-CSRF-TOKEN. ASP.NET verifies that the pair matches the current identity. React does not read either HttpOnly cookie.

The global ApiAntiforgeryFilter applies to unsafe methods, including anonymous login/registration. It skips GET, HEAD, OPTIONS, and TRACE. GET endpoints in this application do not modify records.

Why refresh the token after login?

The token obtained before login belongs to the anonymous identity. Login changes that identity. The client clears its token cache after login, registration, and logout. The next write obtains a fresh token.

If another tab changes the session, a token may become stale. A 400 with code csrf_token_invalid triggers one token refresh and retry. The client does not retry arbitrary errors. The filter rejects CSRF before the controller runs, so this retry cannot duplicate an executed write.

A CSRF token is not a login credential. An anonymous browser can get a CSRF token and still receives 401 from protected APIs. The cookie identifies the user; the token protects writes.

SameSite cookies and CSRF validation work together. They do not replace input validation, authorization, HTTPS, or protection from malicious scripts.

Reference: Microsoft: antiforgery protection.

08 • Database

Existing users now support Identity

The original users had integer IDs and relationships to listings, leads, opportunities, and notes. Those IDs and links are preserved. Credential fields are added to the same Users table.

FieldPurpose
NormalizedEmail / NormalizedUserNameConsistent lookup values generated by Identity, with unique indexes.
PasswordHashVersioned hash. Legacy directory users have null and cannot log in using a guessed/default password.
SecurityStampA version marker used to reject older sessions after security-relevant account changes.
ConcurrencyStampHelps detect conflicting account updates.
AccessFailedCount / LockoutEnd / LockoutEnabledTrack failed passwords and temporary lockout.
EmailConfirmed / TwoFactorEnabledFramework state. Email confirmation and MFA user flows are not enabled.

The app has one domain role per user, so IdentityUserContext uses the original Roles table. There is no second AspNetRoles system. Supporting tables do not imply social login, recovery, or MFA are available.

Migration and old accounts

The migration has been applied to the configured development PostgreSQL database. Review its SQL in docs/add-identity-authentication.sql. It trims/normalizes legacy emails, sets stamps and lockout support, and inserts missing public roles without replacing existing IDs.

Existing emails cannot be registered again. Old users need a verified password-provisioning/reset flow, which is not included. Do not assign one shared default password. On another database, case-only or whitespace-only duplicates must be resolved before unique indexes can be created; the migration transaction fails rather than deleting users.

MD5 expressions in the migration generate legacy stamp identifiers, not password hashes. Passwords are processed only by Identity's password hasher.

useState holds the form values. onSubmit prevents default page navigation and calls the service. try/catch/finally handles success, errors, and resetting the pending state.

Session restoration and cancellation

The provider restores the session in an effect. Cleanup aborts requests when it unmounts. A generation counter prevents an older result from overwriting a newer login/logout. This handles React's development Strict Mode effect setup/cleanup too.

Account state is not the password or ticket. Refresh rebuilds it using /me. Browser tools can edit React state, so the backend never accepts that state as authentication proof.

Public pages use existing light tokens: pale surfaces, lavender accents, purple buttons, and dark readable text, with responsive layouts and labeled controls.

10 • Permissions

Login is only the first check

After identifying a user, .NET checks whether that account may access the endpoint. This is independent of the dashboard React displays.

POST /api/auth/registerAnyone + CSRF; rate limited201 account + session
POST /api/auth/loginAnyone + CSRF; rate limited200 account + cookie, or 401
GET /api/auth/meAuthenticated user200 account, or 401

Properties, Contacts, Leads, Opportunities, PipelineStages, Activities, NotesAgent or admin; writes require CSRFExisting CRM operations

Users / Roles mutationsAdmin + CSRFAccount/role administration

AllowAnonymous opens the three pre-login endpoints. The fallback policy requires authentication. Authorize(Roles = "agent,admin") restricts CRM access. ManageUsers requires admin for directory changes.

Public sign-up cannot create admin accounts. No admin or password is seeded. If an admin is provisioned through a trusted process, React opens the agent workspace. There is no separate admin management screen.

Current scope: agents share the CRM workspace; record ownership is not enforced. Buyer/seller dashboards and several business features still use sample data/placeholders. Working authentication does not make every dashboard feature a live API feature.

Before a multi-company deployment, add tenant/ownership checks. Public agent registration fits this portfolio flow; a real agency should decide whether agents require invitations or approval.

12 • Inspect and troubleshoot

See the flow in developer tools

Open F12 → Network. Use a disposable development account: screenshots of request payloads can reveal the password.

  1. auth/csrf: response JSON contains the token; the server may set the antiforgery cookie.
  2. auth/login: POST payload contains email/password/rememberMe. X-CSRF-TOKEN is a request header. Success returns account JSON and a session cookie header.
  3. Application → Cookies: development names are Meridian.Session and Meridian.Csrf, both HttpOnly. Production names start __Host-.
  4. Refresh: auth/me returns 200; the password was not submitted again.
  5. Logout: returns 204; a subsequent session check returns 401.
Status / symptomMeaning and next check
200 / 201 / 204Login or session success / account created / logout success with no body.
400 validationInspect errors: invalid email, password, duplicate account, role, or acknowledgment.
400 csrf_token_invalidMissing/stale/mismatched token. The client refreshes once; check proxy/cookies if it persists.
401Rejected credentials, lockout, or missing/expired session. Anonymous initial /me returning 401 is expected.
403Authenticated but forbidden. Buyer/seller access to agent APIs is rejected.
409Uniqueness, relationship, or concurrency conflict. Simultaneous duplicate registration can hit a database constraint.
429Rate limited. Wait rather than retry repeatedly.
503 during registerRequired roles missing or database unavailable. Check migration, PostgreSQL, and logs.
500Unexpected failure. Use trace ID and backend logs; raw database errors are hidden from the client.
Auth endpoint 404An old API build may be running. Restart it and check API_PROXY_TARGET.
Proxy error / fetch failedStart the API; verify port, development certificate, and target. Production needs its own reverse proxy.
Cookie never savedCheck host, scheme, SameSite, Secure and credentials. Production Secure cookies need HTTPS.
Database column missingRuntime is connected to a database without the migration. Verify both migration and runtime connections.
Legacy password never worksOlder directory entries have no password. Use a new email for study or add verified provisioning/recovery.
Windows Data Protection errorThe process may use another Windows identity or lack access to its protected keys. Run as the intended user; do not blindly delete production keys.

The error UI shows server validation messages when available. Network downtime is different from an invalid password: changing account credentials cannot fix an unavailable API.

13 • Review and next steps

Check your understanding

  1. Why does React not verify passwords? The server owns credential storage and verifies with Identity.
  2. Why does refresh keep you logged in? The browser retains the cookie. /me rebuilds React's account state.
  3. Can editing React's role unlock agent data? No. .NET checks claims in a valid protected ticket.
  4. Is a CSRF token enough for protected APIs? No. Authentication is separate.
  5. Why do equal passwords have different hashes? Each hash uses fresh random salt.
  6. Why no default password for old users? Predictable shared credentials are unsafe. Add verified setup/reset.
  7. 401 versus 403? Authentication missing/rejected versus authenticated without permission.
  8. Remember me? A persistent cookie for the configured 8-hour lifetime; no password storage.

Small exercises

  • Create a buyer and visit /agent/listings. Observe the redirect. A direct /api/Properties request returns 403.
  • Compare requests before/after refresh. Passwords appear during login, not /me.
  • Trace AuthController.Register() dependencies to AuthenticationExtensions.cs.
  • Read AuthenticationTests.cs and connect tests to diagrams in this guide.

Validation completed

The backend suite has 85 passing tests at implementation time. Authentication checks cover anonymous access, real password hashing, safe responses, HttpOnly cookies, sessions, logout/login, email casing, duplicate accounts, password/role validation, missing/tampered CSRF, lockout, role enforcement, admin-only mutations, preserved hashes during directory updates, and rate limiting. Other tests cover the original schema, contracts, CRUD, and error handling. Frontend build and lint validate compilation and code rules.

Features to plan before a public deployment

  • Email confirmation and recovery: mail delivery, expiry-limited confirmation/reset links, and complete UI flows. Forgot password currently explains recovery is unavailable.
  • Agent invitations / trusted admin provisioning: decide who may create agency accounts; never expose public admin registration.
  • Tenant and record ownership: restrict data to the right organization/account. Current agents share the workspace.
  • Deployment: HTTPS, same-origin proxy, persistent protected Data Protection keys shared across API instances, trusted forwarded headers, secrets outside source, database backups, and rate limits appropriate for proxies/replicas.
  • Account lifecycle: consider MFA, breached-password screening, safe audit events, all-device revocation, deletion policies, and formal consent tracking.

Cookie tickets need the right Data Protection keys after restarts and across replicas. Default local Windows key storage supports development; deployment needs an explicit persistence/protection plan. Do not switch to temporary in-memory production keys to silence a key-access error.

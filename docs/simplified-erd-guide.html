How the simplified CRM fits together

This guide describes the backend and React refactor based on real_estate_crm_erd_simplified.html. It keeps your existing light theme and Identity login while aligning the business model with eight entities.

The key change: a person in your CRM is a Contact. A person who can log in is a User. Property sellers and opportunity buyers reference contacts. Contact ownership and property/opportunity agents reference users.

1. A simple example

Taylor is an agent who logs in. Taylor creates Sam as a Seller contact, then lists Sam's property. Pat is a Buyer contact interested in that property. Taylor creates an opportunity for Pat's offer, moves it through pipeline stages, and logs calls and notes.

PK means primary key: the row's own ID. FK means foreign key: an ID pointing to a row in another table. For example, Property.SellerContactId = 12 means contact 12 is the seller. It does not mean user 12 is the seller. The database enforces which table each ID belongs to.

Why are there extra authentication fields/tables? The diagram describes CRM data. Login still needs Identity's password hash, security stamp, lockout fields, and supporting user claims/login/token tables. These are deliberately retained. There are eight CRM entities plus three Identity infrastructure entities; removing credential fields to literally copy the User box would break login.

Notes have a polymorphic reference. For example, EntityType = Opportunity and EntityId = 7 describe opportunity 7. There is no single database FK that points to all possible entity tables. AuthorId is a real FK to Users. Other business relationships use restrictive deletes so deleting a referenced user, contact, property, or stage does not automatically erase related records.

4. Walk through the app

  1. Log in as an agent. Your HttpOnly session cookie authorizes CRM requests. Admin users use the agent workspace; directory mutations still require admin.
  2. Open Contacts → New contact. Create a Seller, choose its owner, and enter Status and Source. The contact does not need a login account.
  3. Open Listings → Add property. The seller dropdown calls Contacts and filters Type = Seller. The agent dropdown calls Users and filters role = agent. Save address, price, bedrooms, status, seller, and agent.
  4. Create a Buyer contact. For an existing prospect, Edit lets you change Type and lifecycle fields.
  5. Open Pipeline. Add stages in order, then create an opportunity with a buyer, property, agent, stage, and offer amount. Select a different stage to save progress.
  6. Select an opportunity card. Log an activity with its contact and time, or add a note. Refresh to see the saved information.

The supplied ERD does not include photos, bathrooms, area, a property type, description, or a separate property name. The add-property form now collects the fields the database can save. Buyer/seller portals and some navigation items remain presentation prototypes; the ERD provides no direct account-to-contact relationship to safely identify a portal user's CRM records.

5. What happens after clicking Save

// React sends Contact IDs for sellers, User IDs for agents.
{
  "address": "123 Sample Street",
  "price": 4200000,
  "status": "Active",
  "bedrooms": 2,
  "sellerContactId": 12,
  "listingAgentId": 3
}
  1. The shared API client obtains CSRF proof and sends the request with credentials.
  2. The server verifies the logged-in user's role. An unauthenticated request returns 401; a forbidden role returns 403.
  3. ASP.NET Core binds JSON into PropertyCreateRequest. Required fields, ranges, and statuses are validated. Invalid input returns 400 field errors before the action saves anything. Obsolete SellerUserId and LeadId fields are rejected on the affected DTOs.
  4. PropertiesController checks that SellerContactId exists in Contacts and has Type = Seller, and that ListingAgentId references an agent user. ContactsController checks its owner exists; OpportunitiesController checks its buyer/property/agent/stage; ActivitiesController checks both references.
  5. AutoMapper maps request fields into the domain model. CrudService saves through ApplicationDbContext; the database enforces real foreign keys.
  6. The saved record is reloaded with relevant related data, mapped to a response DTO, and returned. React updates its table only after success. Failures become visible ApiError messages.

POST creates a record and returns 201. GET reads and returns 200. PUT replaces the editable fields and returns 200. DELETE returns 204 after success; a restrictive relationship can prevent deletion. PUT requires the full request object, including its required foreign keys.

6. Migrating existing data safely

The new version uses an additional migration, 20261011070708_AlignSimplifiedErd. Previously applied migrations are kept. The reviewed SQL is align-simplified-erd.sql.

Existing dataConversion
Contacts without OwnerIdChoose the first related listing agent, otherwise opportunity agent, otherwise converted lead owner. Unlinked records use the first agent, then admin, then another user. No password or fabricated user is created. A database with contacts but no possible owner is rejected.
Unconverted leadsCreate Prospect contacts using source, owner, and Status = New. Split names at the first space; blank last name is allowed. Existing name length limits still apply, and the complete original name and lead fields are archived in a contact note.
Converted leadsKeep the existing Contact ID, set Status = Active, fill unknown source, and archive the original lead fields. Multiple original lead records each retain their own archive note.
Lead activities and notesMap missing activity ContactId to the migrated contact. Move Note references from Lead to Contact while retaining their text. A JSON archive note retains original lead-related activities and notes, including old IDs.
SellerUserId assignmentsReuse a Seller contact with matching email and owner, or create one from the seller account's name/email, owned by its listing agent. Update SellerContactId before removing SellerUserId. Account rows and credentials remain intact; the original property fields are archived in a property note.
Null bedroom countsSet zero, with the original null stored in the property archive note.
Activities lacking a contactUse their migrated lead contact if available, otherwise their existing opportunity's buyer. If either required contact or opportunity is still missing, abort the migration instead of inventing records.
Properties with no seller or a non-Seller contactAbort and request corrected assignments before retrying.

EF runs this migration in a transaction. A guard failure rolls back schema and data changes; sequence counters may advance, which only leaves unused IDs. This migration intentionally has no automatic Down conversion. Restore the full pre-upgrade backup with the matching old application version for rollback; recreating empty legacy tables would lose meaning.

Applied to this workspace: the configured PostgreSQL database had three users and no CRM business records. The migration was applied after a full custom-format backup at artifacts/database-backups/20261011-pre-simplified-erd.dump. All three users were preserved. Restart/rebuild any already-running backend to load the updated model.

The dump includes credentials and account data; keep it local and out of source control. The repository ignores artifacts. Archive notes are part of the database and can be inspected through Notes; keep them when preserving migration history.

7. Verify and repeat the upgrade elsewhere

Run the following from the backend repository. The tool uses appsettings.json, or the CRM_MIGRATION_CONNECTION environment variable. Its backup executable is the installed PostgreSQL 18 pg_dump. The test mode creates only uniquely named temporary schemas, applies the old migrations, seeds fixture data, applies the new migration, checks conversion and rollback, and removes those schemas.

dotnet build tools\SchemaUpgrade\SchemaUpgrade.csproj -c Release -p:UseAppHost=false
# Inspect the configured schema without printing credentials:
dotnet tools\SchemaUpgrade\bin\Release\net8.0\SchemaUpgrade.dll check
# Test conversion in isolated PostgreSQL schemas:
dotnet tools\SchemaUpgrade\bin\Release\net8.0\SchemaUpgrade.dll test
# Save a full database dump; use a new filename for each backup:
dotnet tools\SchemaUpgrade\bin\Release\net8.0\SchemaUpgrade.dll backup artifacts\database-backups\before-upgrade.dump
# Apply the tested migration to the configured database:
dotnet ef database update AlignSimplifiedErd --project CRM\CRM.csproj --configuration Release --no-build
# Verify backend behavior:
dotnet test CRM.sln -c Release -p:UseAppHost=false
# From realestateCRM-client:
npm.cmd run build
npm.cmd run lint

Before applying to another database, inspect and test its data and stop old application writes during the upgrade. The script handles missing ownership and seller-user conversion, but intentionally rejects unresolved sellers and activities. Microsoft recommends reviewing migrations and testing their data impact before applying them: managing migrations, applying migrations.
